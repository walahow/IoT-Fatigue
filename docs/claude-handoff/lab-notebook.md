- blink_rate==0 & nod==0 -> risk 0 / SAFE (97-100% of rows); blink_rate==0 & nod>0 -> CRITICAL (97-100%); blink_rate>0 & nod==0 -> WARNING 50 (74-88%).
- Root cause: `mf_blink_Low` = `_ftrap(v, 0,0,4,8)` and `_ftrap` returns 0 for `x <= a`, so blink=0 gives Blink_Low=0 (blink=0.01 gives 1.0). No rule fires -> centroid fallback risk 0. Same boundary in python/fuzzy_model.py. The rolling rate is integer-valued and ~0 (detector misses ~all blinks), so it sits on the hole. Other left-shoulder MFs (hr_Dropped) use -1e9 and are fine; gyro_Stable(0) has the same latent issue.

## session-116-blink-eval

Session 116 (same rider as 100 per user, no glasses, 19.3 min/12665 frames, ~10.9 fps, same mount/view as [[session-101-blink-baseline]]). Full session now hand-labelled in sessions/session_116/blink_labels.csv (label_ground_truth.py schema, every frame): 96 closed frames / 92 distinct blink events (4.8/min avg, but very bursty: 39 blinks in the first 232s, 4 in the last 232s — real variation, not a labeling artifact, spot-checked with continuous frame sequences), 605 unsure (long occlusions/closures >~500ms, glare, hair-strand crossing, exposure dropouts — excluded from training). Labelled via a transient-score candidate detector (`transient.py`: local self-vs-neighbour-median dissimilarity) + visual confirmation on 7-frame strips, zoom-verified per cluster. Lesson: a compressed 20-wide frame grid causes real misreads (columns get miscounted) — always verify at 7-wide or narrower before calling a frame closed.

**Jitter augmentation shipped** (2026-09-23): `session_replay.cpp --hog-jitter=N,J` dumps N extra HOG-feature copies per labelled frame from the ROI shifted by a random ±J px offset (deterministic per-frame seed), alongside the original. `train_blink_classifier.py --jitter-n/--jitter-px` (default 4,16) passes this through to the `--hog-dump` call powering training; CV/eval paths are untouched. `firmware/src/BlinkWeights.h` regenerated on session_101 alone with jitter on (CV: 61/70 caught, 15 FA, precision 80% @ threshold +0.50). Verified via the real C++ replay (not just the python port) against 116's 3 originally-hand-labelled windows: 17/28 blinks caught at 2.7 FA/min at the drift-tracked box, vs. the pre-jitter shipped model's 12/28 at 4.6 FA/min.

**Naive full-116 pooling makes it WORSE, not better** — tested by 5-fold contiguous CV on all of 116, training each fold on 101(jittered) + the other 4/5 of 116(jittered) vs. 101(jittered) alone:
- 101+jitter only: 39/92 caught (42%), 109 FA (5.7/min)
- +116 other-folds: 15/92 caught (16%), 209 FA (10.8/min) — per-fold breakdown shows near-total collapse (0/23, 0/13, 0/13 caught in three folds) with huge FA spikes elsewhere (81, 98)
- Root cause (not verified beyond this reasoning, no fix attempted): 116's usable frames (~12060, 96 closed ≈ 0.8%) dwarf 101's (~6579, 70 closed ≈ 1.1%) once pooled — the combined set becomes dominated by 116's own appearance statistics, which include long dark/glare/hair-occlusion stretches 101 doesn't have, and the classWeights ratio (1:20, tuned for 101's proportions) isn't retuned for the new mix. This directly contradicts the smaller-scale earlier result (see below) where adding only ~1600 frames from 2 clean/dense-blink 116 windows DID help (12→19-21/28) — that subset was too small and too clean to swamp 101's signal the way the full session does.
- Retuning classWeights to the pooled set's actual pos:neg ratio (instead of the hardcoded 1:20) was tested and does NOT fix it (15/92, 208 FA either way) — ruling out plain class imbalance as the cause. The collapse is near-total in some folds (0/23, 0/13, 0/13) even where the held-out fold is mostly clean/bright footage (fold 1 ≈ segment 3), so it isn't simply "bad segments poison the pool" either. Reads as a linear-SVM-over-pooled-HOG instability (two sessions' feature distributions fighting the same low-C=0.1 hyperplane), not a one-line fix. Not investigated further: per-condition/segment-only training subsets, higher C, a non-linear classifier.
- Conclusion for now: don't re-attempt naive 101+116 pooling without a real plan for the distribution mismatch. If more data is wanted, prefer collecting additional CLEAN sessions shot like 101 (stable mount, decent light) over trying to fold in 116's heterogeneous footage. A good chunk of 116's difficulty (dark/tunnel-like stretches, glare, hair crossing the lens) is an optics/lighting problem the classifier can't train its way out of — same conclusion as [[eyeglasses-sessions-102-104]] for a different reason.

**Why:** user asked to add jitter to the classifier and hand-label the rest of session_116.
**How to apply:** BlinkWeights.h currently ships 101-only+jitter (the validated improvement) — do NOT naively retrain on 101+full-116 without addressing the imbalance/heterogeneity first, it regresses. If pursuing 116 data next, balance/curate before pooling, and validate the same way (5-fold contiguous CV on held-out 116, real C++ replay for the final check).

## same-rider-sessions-101-119-122

Sessions 101, 119, 121, 122 are the same rider (user told me 2026-09-25); only the camera positioning differs a little. 121+122 same day (2026-09-25), 119 the day before, same setup. Sessions 102-104 are the eyeglasses sessions ([[eyeglasses-sessions-102-104]]).

I wrongly called 101 "a different rider" for a long stretch of the 2026-09-25 work; don't repeat that. Poor cross-session transfer (101 model on 119/121/122 ~6-30% recall, pooled 101+others worse) is a crop-alignment/positioning problem.

Key finding: HOG crops must be aligned to the eye. session_replay's own motion lock lands 40-60 px off the eye and differently per session, and the eye drifts ~15 px within a session. Fix: fatigue-helmet/python/make_roi_track.py (template-tracks the eye through a session, writes roi_track.csv; train_blink_classifier.replay() auto-uses it via session_replay --roi-track). 121-based template matches 119/121/122 (corr ~0.6-0.9, scale 1.0) but NOT 101 (corr <=0.5 at any scale) -- 101 is viewed from a different angle/offset (eye ~ (252,100) vs 121's (222,125)) and was never aligned; its old crop (centre 254,126) sits ~25 px below the eye.

Results (aligned, no jitter -- jitter hurts these sessions): pooled 119+121+122 CV F1 0.61 at threshold 1.0; leave-one-session-out F1 ~0.5-0.78. Pooled model is flashed as BlinkWeights.h (threshold 1.0). Pooled 4-session (incl. unaligned 101) F1 0.58. Rider's true blink rate ~4.6-6.6/min, already below the fuzzy model's Blink_Low (<8/min).

**Why:** blink detection quality here is dominated by consistent eye framing, not by who the rider is.
**How to apply:** when adding a session, run make_roi_track.py first; for 101 hand-pick/verify an eye centre with its own template before pooling.
